# Fresh 0.2.0 Storage Progress

This document tracks the implementation of the pluggable, Fresh-managed storage architecture planned for Fresh 0.2.0.

## Target

Fresh 0.2.0 will allow applications to select a built-in storage backend through `FreshConfig`. Fresh will create, mount, own, unmount, and destroy the selected backend.

Initial supported backends:

- LittleFS
- SD over SPI using ESP-IDF
- SD over SDMMC using ESP-IDF where supported

The database and application-managed backup archives will use the same selected filesystem. Cross-filesystem migration and copying are outside the 0.2.0 scope.

### Public API

```cpp
FreshConfig config;
config.storageType = FreshStorageType::SD;
config.sd.interface = FreshSDInterface::SPI;

Fresh database;
FreshResult result = database.init("/fresh", config);
```

SD configuration is public, but `Fresh::init()` temporarily rejects SD until Milestone 4 removes every direct LittleFS call from the persistence engine. This prevents a partially migrated database from writing to the wrong filesystem.

## Explicitly deferred beyond 0.2.0

- Automatic migration between filesystems
- Simultaneous database storage across multiple filesystems
- Automatic SD-to-LittleFS fallback
- SD card hot-swap recovery
- Automatic remount after card replacement
- Network, USB, or remote storage backends
- Backup archive copying between filesystems

## Current implementation notes

- `FreshConfig` now contains `storageType`, `littleFS`, and `sd` configuration.
- Fresh creates and owns the selected backend through `FreshStorageFactory`.
- The normal zero-configuration path still selects LittleFS.
- LittleFS mount, capacity reporting, rollback cleanup, and deinitialization now use `FreshLittleFSStorage`.
- `FreshFile` provides the VFS/POSIX file boundary required by both LittleFS and FATFS.
- `FreshStorage` provides logical path validation, directory operations, file opening, and tracked-handle protection.
- SDSPI mounting and lifecycle management are implemented with ESP-IDF APIs.
- SD selection remains deliberately gated in `Fresh::init()` because journals, snapshots, manifests, durable restore, and garbage collection still use the global Arduino LittleFS object.
- The alternate manifest slot remains the durable restore commit boundary.
- Storage formatting must always be explicitly enabled. SD formatting remains disabled by default.

## Next development step

Migrate `FreshStorage.cpp` to `FreshStorage` and `FreshFile`, beginning with durable-slot reads/writes, journal append/replay, directory creation, storage-space preflight, and snapshot cleanup. Once that path is backend-neutral, migrate durable restore and garbage collection, remove the SD gate, and switch LittleFS mounting from the Arduino compatibility adapter to direct ESP-IDF VFS registration.
