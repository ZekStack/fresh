# Fresh 0.2.0 Storage Progress

This document tracks the pluggable storage architecture planned for Fresh 0.2.0.

## Target

Fresh 0.2.0 must support the same database, backup, restore, and garbage-collection behavior on:

- Fresh-managed LittleFS
- Fresh-managed SD over SPI
- Fresh-managed SD over SDMMC where supported
- Fresh-owned custom storage backends
- Caller-owned custom storage backends

All persistence operations must use the selected `FreshStorage` backend. The database and application-managed backup archives use the same storage instance. Cross-filesystem migration and archive copying are outside the 0.2.0 scope.

### Built-in managed storage

```cpp
FreshConfig config;
config.storageType = FreshStorageType::SD;
config.sd.interface = FreshSDInterface::SPI;
config.sd.spi.chipSelectPin = GPIO_NUM_10;
config.sd.spi.clockPin = GPIO_NUM_12;
config.sd.spi.mosiPin = GPIO_NUM_11;
config.sd.spi.misoPin = GPIO_NUM_13;

Fresh database;
FreshResult result = database.init("/fresh", config);
```

### Fresh-owned custom storage

```cpp
std::unique_ptr<FreshStorage> storage = createCustomStorage();
FreshResult result = database.init("/fresh", std::move(storage));
```

Fresh mounts, unmounts, and destroys this backend.

### Caller-owned custom storage

```cpp
CustomStorage storage;
storage.attach();

FreshResult result = database.init("/fresh", storage);
```

The custom storage must already be mounted. Fresh attaches a reference adapter, never unmounts the caller-owned backend, and detaches its adapter during deinitialization.

## Explicitly deferred beyond 0.2.0

- Automatic migration between filesystems
- Simultaneous database storage across multiple filesystems
- Automatic SD-to-LittleFS fallback
- SD card hot-swap recovery
- Automatic remount after card replacement
- Network, USB, or remote storage implementations bundled into Fresh
- Backup archive copying between filesystems

Custom implementations of network, USB, encrypted, or other storage are supported through `FreshStorage`; Fresh simply does not bundle those transports in 0.2.0.

## Current implementation notes

- Built-in and custom backends now use one persistence engine.
- `FreshFile` is no longer tied to Arduino `File` or POSIX `FILE*`.
- Built-in backends use ESP-IDF VFS and POSIX through the default file backend.
- Custom backends may use any storage mechanism by implementing `FreshStorage` and `FreshFileBackend`.
- LittleFS, SDSPI, and SDMMC are managed by Fresh when selected through configuration.
- Fresh-owned custom storage is mounted, unmounted, and destroyed by Fresh.
- Caller-owned custom storage remains mounted and is only attached/detached by Fresh.
- The database and backup archives remain on the same storage instance.
- Storage formatting is always opt-in. SD formatting remains disabled by default.
- The alternate manifest slot remains the durable restore commit boundary.
